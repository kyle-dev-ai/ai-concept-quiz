# 문항 자동 검수

`npm run eval`은 형식과 회귀만 본다. 이 스킬은 그 게이트가 구조적으로 잡을 수 없는 것을 본다.

> **골든 케이스는 승인된 문구를 substring으로 지키는 회귀 잠금장치다. 새로 들어온 틀린 문장은 형식만 맞으면 통과한다.**
> 그래서 사실 검증은 사람 또는 이 검수가 해야 한다.

## 세 가지 축

| 축 | 묻는 것 | 실패하면 생기는 일 |
|---|---|---|
| **사실** | 틀린 설명이 있는가 | 학습자가 면접에서 틀린 답을 자신 있게 말한다 |
| **말투** | AI가 찍어낸 티가 나는가 | 읽다 지치고 앱을 신뢰하지 않는다 |
| **범용성** | 대학원 준비생 말고도 쓸 수 있는가 | 출시해도 특정 소수만 쓴다 |

## 실행 순서

### 1. 검수 범위 정하기

인자로 받는다. 없으면 사람 검수 대기 문항을 기본으로 한다.

| 인자 | 범위 |
|---|---|
| (없음) | `docs/content/sources.md`에서 "사람 사실 검수 대기"로 기록된 배치 전체 |
| `all` | 전체 문항 |
| `1.5.0` | 해당 dataset 배치에서 추가된 문항 |
| `rag` | 해당 카테고리 |
| `id1,id2` | 지정한 문항 |

범위가 40문항을 넘으면 카테고리별로 나눠 여러 번 돌린다. 한 에이전트에 너무 많이 주면 뒤쪽 문항을 대충 본다.

### 2. 질문 은행 최신화

```bash
npm run build:content
```

검수 대상은 항상 **빌드된 질문 은행 JSON**이다. TS 소스가 아니라 실제로 앱에 실리는 파일을 봐야 한다.

### 3. 기계 검사 먼저

구조 결함은 `npm run verify`에 이미 편입돼 있다(`check:content`). 카테고리별 진입로 부재,
덱 밖 선수 요구, 난이도 역전, 골든 케이스 없는 문항이 **새로 늘어나면 빌드가 실패한다.**
그러니 이 검수에서는 그 항목을 다시 세지 말고, 게이트가 잡지 못하는 것에 집중한다.


```bash
node scripts/audit-content-style.mjs               # 전체
node scripts/audit-content-style.mjs --ids=a,b,c   # 지정 문항
```

길이, 문장 수, 핵심 포인트가 답변을 그대로 반복하는지, 표현 반복률, 꼬리질문 단조로움, 문항 간 문장 복제, 카테고리별 난이도 공백을 센다. **셀 수 있는 것을 에이전트에게 판단시키지 않는다.** 이 결과를 아래 에이전트에게 함께 넘긴다.

### 4. 검수 에이전트 3종 병렬 실행

세 축을 각각 다른 에이전트에게 맡긴다. 한 에이전트에게 다 시키면 사실 검증이 흐려진다. `run_in_background: false`로 돌려 결과를 받고 진행한다.

#### A. 사실 검증관

```
너는 AI/ML 학습 콘텐츠의 사실 검증자다. 회의적으로 읽어라.

대상: <문항 JSON>

각 문항의 10초 답변, 심화 답변, 핵심 포인트에서 다음을 찾아라.
1. 기술적으로 틀린 서술
2. 2026년 기준으로 낡은 서술
3. 지나치게 단순화해서 결과적으로 틀린 것
4. 조건을 빼먹어 특정 상황에서만 참인데 일반 사실처럼 쓴 것
5. 용어를 표준과 다르게 쓴 것

특히 다음은 반드시 근거를 확인해라.
- 수식 기호, 차원, 축, 부호
- "항상", "모든", "무조건" 같은 단정
- 학습 단계와 추론 단계의 경계
- 벤더 고유 개념을 일반 표준처럼 서술한 것
- 근사인 기법과 정확한 기법을 뒤섞은 것

지적마다 다음을 써라: 문항 ID · 문제 문구 원문 · 왜 틀렸는지 · 고친 한국어 문장.
확신이 없으면 "확인 필요"로 표시하고 단정하지 마라.
자잘한 취향 문제는 빼라. 학습자가 틀리게 배우는 것만 보고해라.
```

#### B. 말투 검사관

```
너는 한국어 기술 글의 편집자다. AI가 쓴 티가 나는 문장을 찾아라.

대상: <문항 JSON> + <기계 검사 결과>

한국어에서 AI 말투의 징후:
- 모든 문장이 "~합니다"로 같은 길이·같은 구조로 끝난다
- "~할 수 있습니다", "~해야 합니다"가 문단마다 반복된다
- 번역투: "~에 대한", "~을 통해", "~에 있어서", "~라고 할 수 있습니다"
- 명사화 과다: "확인이 필요합니다"(X) → "확인해야 합니다"(O)
- 나열 강박: 필요 없는데 항상 세 가지씩 병렬로 늘어놓는다
- 과잉 완충: "일반적으로", "대체로", "경우가 많습니다"를 습관처럼 붙인다
- 사람이 말로 하지 않는 문어체가 10초 "구술" 답변에 들어 있다
- 문항마다 같은 리듬으로 시작한다 (예: 전부 "~때문입니다"로 끝남)

이 앱의 10초 답변은 **소리 내어 말하는 것**이다. 눈으로 읽는 글이 아니다.
그 문장을 실제로 입으로 말했을 때 어색하면 지적해라.

지적마다: 문항 ID · 원문 · 무엇이 어색한지 · 자연스럽게 고친 문장.
고친 문장은 반드시 같은 의미를 유지해야 한다. 사실을 바꾸지 마라.
```

#### C. 범용성 검사관

```
너는 이 앱을 출시할지 판단하는 제품 검토자다.
앱은 "AI 개념을 10초간 소리 내어 설명하고 스스로 평가하는" 학습 앱이다.

대상: <문항 JSON> + <카테고리별 난이도 분포>

세 사람의 눈으로 읽어라.
1. AI를 처음 공부하는 직장인 — 첫 문단에서 막히는 문항은 어디인가
2. 이직 준비 중인 개발자 — 실무에 쓸모없어 보이는 문항은 어디인가
3. 대학원 구술 준비생 — 너무 얕아 도움이 안 되는 문항은 어디인가

확인할 것:
- 설명 없이 던지는 용어가 있는가 (그 용어를 다루는 선수 문항이 실제로 있는가)
- 특정 배경(대학원 준비, 특정 직무)을 가정해야만 이해되는 문항이 있는가
- 카테고리별로 기초→중급→심화 사다리가 끊긴 곳이 있는가
- 같은 개념을 여러 문항이 중복해서 다루는가
- 학습자가 "이건 왜 배우지"라고 물을 문항이 있는가

마지막에 한 문장으로 답해라: 이 문항들은 불특정 다수에게 공개해도 되는 수준인가?
근거 없이 좋다고 하지 마라. 안 되면 무엇이 부족한지 말해라.
```

### 5. 지적 사항 반박 검증

에이전트 셋이 낸 지적을 그대로 믿지 마라. **사실 지적만** 따로 모아 반박을 시도한다.

```
다음 지적이 정말 오류인지 반박해라. 반박할 수 없을 때만 인정해라.
원 문장이 맥락 안에서 맞을 가능성, 지적한 쪽이 틀렸을 가능성을 먼저 검토해라.

지적: <내용>
원문: <문항 전체>

판정: 확실한 오류 / 정밀도 문제 / 취향 / 지적이 틀림
```

이 단계를 건너뛰면 취향 문제가 오류로 보고돼 멀쩡한 문장을 고치게 된다.
말투·범용성 지적은 반박 검증 없이 제안으로 다룬다.

### 6. 보고서 작성

`docs/content/audit-<dataset version>-<날짜>.md`에 남긴다.

```markdown
# 문항 검수 <dataset version> · <날짜>

- 검수 범위: N문항
- 판정: 출시 가능 / 조건부 / 보류
- 반드시 고칠 것 N건 · 고치면 좋은 것 N건

## 반드시 고칠 것 (사실 오류)
### 1. `문항 ID` — 한 줄 요약
- 원문: "..."
- 문제: 왜 틀렸는가
- 수정: "..."

## 고치면 좋은 것 (말투·범용성)
...

## 기계 검사 요약
...

## 범용성 판정
...
```

### 7. 수정 적용과 재검증

수정은 TS 소스(`src/content/roadmap-questions/*.ts`)에 하고, 다음을 반드시 확인한다.

1. **골든 케이스가 깨지는지 본다.** 수정한 문장이 골든 케이스의 `requiredConcepts`에 쓰인 문구라면 `assets/evals/golden-set.v1.jsonl`도 함께 고쳐야 한다.
2. `npm run verify` 통과
3. `docs/content/sources.md`의 해당 배치에 검수 완료를 기록한다

## 판정 기준

| 판정 | 조건 |
|---|---|
| **출시 가능** | 사실 오류 0건, 범용성 검사관이 공개 가능하다고 판단 |
| **조건부** | 사실 오류가 있지만 수정이 문항 내부에서 끝남 |
| **보류** | 개념 자체가 잘못 잡혔거나 카테고리 사다리가 끊겨 재설계가 필요함 |

## 자동화된 것과 아닌 것

| 검사 | 어디서 | 새 결함을 막는가 |
|---|---|---|
| 형식·ID·prerequisite 존재·금지 markup | `npm run eval` | 예 |
| 골든 케이스 문구 회귀 | `npm run eval` | 예 |
| 진입로 부재·덱 도달성·난이도 역전·골든 미커버 | `npm run check:content` | 예 (baseline 대비 증가분) |
| 길이·문장 수·표현 반복·문항 간 복제 | `npm run audit:style` | 아니오 (보고만) |
| **사실 정확성** | 이 스킬 | 아니오 |
| **말투의 자연스러움** | 이 스킬 | 아니오 |
| **초심자 가독성** | 이 스킬 | 아니오 |

아래 세 줄이 이 스킬이 존재하는 이유다. 나머지는 기계가 한다.

## 하지 말 것

- 사실 검증과 말투 교정을 한 에이전트에게 같이 시키지 마라. 말투를 고치다 사실이 바뀐다.
- 기계가 셀 수 있는 것을 에이전트에게 세게 하지 마라. 느리고 부정확하다.
- 지적 건수를 성과로 보지 마라. 취향 지적이 늘면 진짜 오류가 묻힌다.
- 검수 없이 통과시킨 문항을 "eval GO"라는 이유로 검증됐다고 기록하지 마라.
